#### Multiple currencies per domain ([#{pullRequestId}](https://github.com/shopsys/shopsys/pull/{pullRequestId}))

- add the required `currencies` key to every domain in your `config/domains.yaml` **before running the database migrations** — the first currency in the list must be the currency you previously had selected as the domain default currency in the administration:
    ```yaml
    domains:
        - id: 1
          name: shopsys
          locale: en
          currencies: [EUR]
    ```
- the per-domain default currency is now read from the configuration instead of the database:
    - the `defaultDomainCurrencyId` and `freeTransportAndPaymentPriceLimit` setting values are deleted by the migrations, and the per-domain default currency selection was removed from the currency settings in the administration (the global default currency used as the exchange rate base stays in the administration)
    - removed `Shopsys\FrameworkBundle\Model\Pricing\PricingSetting::DEFAULT_DOMAIN_CURRENCY` and `FREE_TRANSPORT_AND_PAYMENT_PRICE_LIMIT` constants along with their getter/setter methods, and `Shopsys\FrameworkBundle\Model\Pricing\Currency\CurrencyFacade::setDomainDefaultCurrency()`
    - `Shopsys\FrameworkBundle\Model\Pricing\Currency\CurrencyFacade::getDomainDefaultCurrencyByDomainId()` keeps its name and semantics, but reads the domain configuration now
    - `Shopsys\FrameworkBundle\Component\Domain\Config\DomainConfig::__construct()` has a new `$currencyCodes` parameter, and new methods `getCurrencyCodes()`, `getDefaultCurrencyCode()`, and `hasCurrencyCode()`
- the database migrations add a currency dimension to the stored prices (`product_manual_input_prices`, `transport_prices`, `payment_prices`, `promo_code_limit`, `price_list_product_prices`), create the `free_transport_and_payment_price_limits` table, and add `orders.currency_exchange_rate` and `carts.currency_code` columns
    - transport prices, payment prices, promo code limits, and free transport limits for the secondary currencies of your domains are converted from the default currency by the exchange rate **once** during the migration — review the converted amounts in the administration afterward
- a full Elasticsearch product reindex is required — the product `prices` and `special_prices.prices` mappings contain a new `currency_code` field, and the prices are exported per currency (run `php phing elasticsearch-index-recreate elasticsearch-export`)
    - if you have extended `Shopsys\FrameworkBundle\Model\Product\Search\FilterQuery`, add the `currency_code` match to your custom painless scripts; the `FilterQuery` constructor has a new `$currencyCode` parameter
- `Shopsys\FrameworkBundle\Model\Pricing\Price` now optionally carries its currency:
    - `new Price(Money $priceWithoutVat, Money $priceWithVat, ?Currency $currency = null)`, new `PriceInterface::getCurrency()` method
    - `Price::add()` and `Price::subtract()` throw `Shopsys\FrameworkBundle\Model\Pricing\Exception\CurrencyMismatchException` when combining prices with different currencies — convert prices to a single currency first
- if you create any of the following entities in your code, add the `Currency` constructor argument: `ProductManualInputPrice`, `TransportPrice`, `PaymentPrice`, `PromoCodeLimit` (also new `#[ORM\Id]` columns), `PriceListProductPrice` (via its data factory)
- adjust calls of the changed pricing method signatures:
    - `Shopsys\FrameworkBundle\Model\Pricing\BasePriceCalculation::calculateRoundedBasePrice()` has a new optional `$currency` parameter
    - `Shopsys\FrameworkBundle\Model\Payment\PaymentPriceCalculation::calculatePrice()` and `calculateIndependentPrice()` take the `Currency` instead of the rounding parameters
    - `Shopsys\FrameworkBundle\Model\Transport\TransportPriceCalculation::calculatePrice()`, `TransportPriceRepository` and `TransportFacade` price lookups take the `Currency`
    - `Shopsys\FrameworkBundle\Model\Payment\Payment::setPrice()`, `getPrice()`, and `hasPriceForDomainAndCurrency()` take the `Currency`; `PaymentFacade` price getters were renamed to `*IndexedByDomainIdAndCurrencyCode()`
    - `Shopsys\FrameworkBundle\Model\TransportAndPayment\FreeTransportAndPaymentFacade` methods take the `Currency`, and the price limits are stored in the new `FreeTransportAndPaymentPriceLimit` entity instead of a setting value
    - `Shopsys\FrameworkBundle\Model\Pricing\SpecialPrice\SpecialPriceRepository` methods and `SpecialPriceFactory::createWithCalculations()` take the target (and optionally source) `Currency`
    - `Shopsys\FrameworkBundle\Model\Product\Pricing\PriceFactory::createProductPriceFromArrayByPricingGroup()` has a new optional `$currencyCode` parameter
- the data objects were reshaped for the per-currency administration forms: `ProductInputPriceData::$manualInputPricesByPricingGroupIdAndCurrencyCode`, `PaymentData::$pricesIndexedByDomainIdAndCurrencyCode`, `PriceWithLimitData::$pricesByCurrencyCode`, and `PromoCodeData::$limitsByCurrencyCode` (replaces `PromoCodeData::$limits`)
- orders now snapshot their currency exchange rate — `Order::$currencyExchangeRate` and `OrderData::$currencyExchangeRate` were added, and the order statistics in the administration convert the order totals by the snapshotted rate
    - `Shopsys\FrameworkBundle\Model\Order\Processing\OrderProcessor` fills the currency fields from the currently selected currency when `OrderData::$currencyCode` is not set — custom order processing middlewares must read the currency from `OrderData::$currencyCode` instead of the domain default currency
- new parameter `shopsys.pricing.product_prices_multicurrency_mode` (values `calculated` — the default, secondary currency prices are calculated by the exchange rate, or `manual` — the prices are entered per currency)
    - in the manual mode, the product prices are all-or-nothing per pricing group (validated by the `PricesForAllCurrenciesOrNone` constraint), and the price list import/export CSV contains a new required `currency_code` column
- add the new `currencies-data-create` phing target to your custom `build.xml` if you override the build (it is a dependency of `domains-data-create` and creates the configured currencies idempotently); the currencies configured in `domains.yaml` cannot be deleted in the administration
- the product feed layer supports per-currency generation — `FeedExport`, `FeedExportFactory`, `FeedFacade`, `FeedPathProvider`, and `FeedCronModule` methods have a new `$currencyCode` parameter, and the `shopsys.feed` tag supports a new `currencies` attribute; feeds generated in a secondary currency get a lowercase currency code suffix in the file name (e.g., `mergado_1_czk.xml`)
- GoPay payment methods are now downloaded and stored per currency of the domain — the `gopay_payment_method_unique` index includes `currency_id`, and a payment whose GoPay method currency differs from the currently selected currency is hidden on the storefront
- Frontend API:
    - the currency of the returned prices is resolved from the new `X-Currency-Code` HTTP header with a silent fallback to the domain default currency
    - GraphQL schema additions: `Price.currencyCode`, `PricingSetting.currentCurrencyCode`, `PricingSetting.availableCurrencies`, `CurrencySetting` type, `Order.currencyCode`, and `Order.exchangeRate`
    - `PricingSetting.minimumFractionDigits` now follows the currently selected currency (unchanged when the header is not sent)
    - order prices are always returned in the currency of the order
- see #project-base-diff to update your project
