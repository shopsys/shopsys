#### Rate limit password recovery requests by IP and e-mail ([#4785](https://github.com/shopsys/shopsys/pull/4785))

- [features moved](#movement-of-features-from-project-base-to-packages) from project-base to the frontend-api package:
    - `CustomerUserPasswordRecoveryMutation` implementation (`Shopsys\FrontendApiBundle\Model\Mutation\Customer\User\CustomerUserPasswordRecoveryMutation`) - keep your `App\FrontendApi\Mutation\Customer\User\CustomerUserPasswordRecoveryMutation` as an empty class extending the new base class and re-apply your customizations of `requestPasswordRecoveryMutation()` or `recoverPasswordMutation()` as overrides
- `Shopsys\FrontendApiBundle\Model\Mutation\Customer\User\CustomerUserPasswordRecoveryMutation` now requires the `frontend_api_password_recovery_ip` and `frontend_api_password_recovery_email` rate limiters - until you add the configuration below, the container will not compile after upgrading the frontend-api package
- register the `frontend_api_password_recovery_email` (10 requests per hour) and `frontend_api_password_recovery_ip` (40 requests per hour) sliding window limiters under `framework.rate_limiter` in `app/config/packages/rate_limiter.yaml`
- register the `frontend_api_password_recovery_rate_limiter_cache` pool under `framework.cache.pools` in `app/config/packages/cache.yaml` and the `frontend_api_password_recovery_rate_limiter` client in `app/config/packages/snc_redis.yaml` - keep the client prefix without `%build-version%`, otherwise every deploy resets the anti-abuse budget
- add `@snc_redis.frontend_api_password_recovery_rate_limiter` to `$persistentClients` of `Shopsys\FrameworkBundle\Component\Redis\RedisFacade` - clients missing from that list are wiped by `shopsys:redis:clean-cache`, which the `clean-redis` phing target runs as a dependency of `db-migrations`, so without this the budget is reset on every deploy no matter what prefix you use
- override the same pool with `cache.adapter.filesystem` in `app/config/packages/test/cache.yaml` - an array adapter is wiped by the service reset the test client performs between requests, so your functional tests would never reach the limit
- pass `@limiter.frontend_api_password_recovery_ip` and `@limiter.frontend_api_password_recovery_email` as `$passwordRecoveryIpRateLimiter` and `$passwordRecoveryEmailRateLimiter` to your own subclass in `app/config/services.yaml` - the limiter services are not autowirable
- make sure `TRUSTED_PROXIES` lists your proxies, otherwise Symfony resolves the proxy address as the client IP and a single exhausted IP budget blocks all of your customers
- review the default limits before going live - both limiters are consumed before the input validation runs, so that invalid input cannot be used to bypass them, which also means that:
    - failed attempts (typos, e-mails of non-existing accounts) are counted towards the limit as well
    - visitors sharing an IP (NAT, corporate proxy, CGNAT) share the IP budget
- the `RequestPasswordRecovery` and `RecoverPassword` mutations can now fail with `Shopsys\FrontendApiBundle\Model\Mutation\Customer\User\Exception\TooManyPasswordRecoveryAttemptsUserError` (user error code `too-many-password-recovery-attempts`) - handle the new code in all of your Frontend API consumers
- if you override `recoverPasswordMutation()`, consume `$this->passwordRecoveryIpRateLimiter` at the very top of it, before `$validator->validate()` - the `ExistingEmail` constraint on `RecoverPasswordInput` reports whether the account exists, so a limit consumed after the validation would keep leaking that in the rejected response
- count `RecoverPassword` in when you change the `frontend_api_password_recovery_ip` limit - both mutations share that budget, so setting the new password costs the customer a token on top of the one asking for the link
- see #project-base-diff to update your project
