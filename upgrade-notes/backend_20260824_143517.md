#### Public form mutations can be protected against spam bots by FormSpamProtectionFacade ([#{pullRequestId}](https://github.com/shopsys/shopsys/pull/{pullRequestId}))

- `\Shopsys\FrontendApiBundle\Model\Mutation\ContactForm\ContactFormMutation::__construct()` has a new argument `$formSpamProtectionFacade` (`\Shopsys\FrontendApiBundle\Model\SpamProtection\FormSpamProtectionFacade`) — if you have extended this class, add it to your signature
- the `ContactFormInput` GraphQL input type has a new optional `subject` field acting as a honey pot; when it is filled in, the mutation logs the hit, skips sending the email and still returns `true`, so that a bot cannot tell it was detected
    - if you call the `ContactForm` mutation from your own client, keep the field empty or omit it
- the mutation throws `\Shopsys\FrontendApiBundle\Model\SpamProtection\Exception\TooManyFormSubmissionsUserError` (user error code `too-many-form-submissions`) after 3 submissions from one IP address within 5 minutes; change `framework.rate_limiter.frontend_api_form_spam_protection` in your project configuration to adjust the values
- to protect another public form mutation, add a case to `\Shopsys\FrontendApiBundle\Model\SpamProtection\SpamProtectedFormEnum`, make its input type inherit `HoneyPotInputObject` and call `\Shopsys\FrontendApiBundle\Model\SpamProtection\FormSpamProtectionFacade::shouldDiscardSubmission()` as the first thing in the mutation, see [Protecting a Form Against Spam](https://docs.shopsys.com/en/latest/cookbook/protecting-a-form-against-spam/)
    - all protected forms share the `frontend_api_form_spam_protection` limiter and count on their own keys; override `FormSpamProtectionFacade::getRateLimiterFactory()` to give one form a limiter of its own
- declare the limiter with an explicit Redis-backed `cache_pool`; a limiter without one falls back to `cache.app`, which is stored on the filesystem of a single application instance, so the limit is multiplied by the number of instances and reset on every deploy
    - in the test environment the pool must not use `cache.adapter.array` either, because that one is thrown away on every kernel reboot and a functional test would never reach the limit
- make sure `framework.trusted_proxies` (the `TRUSTED_PROXIES` environment variable) matches your CDN or load balancer, otherwise the per-IP limit either blocks all visitors as one address or can be bypassed by spoofing `X-Forwarded-For`
- `Tests\App\Test\ApplicationTestCase` now gives every test method its own random `REMOTE_ADDR`, so that test methods do not share the quota of an IP based rate limiter — pass `REMOTE_ADDR` in the client options of a test that needs a particular address
- the service resource pattern of `ShopsysFrontendApiBundle` now registers `*Enum.php` classes as services as well — if you have registered such a class of the `Shopsys\FrontendApiBundle` namespace manually, remove your definition
- `\Shopsys\FrontendApiBundle\Model\Resolver\Store\StoresQuery::__construct()` takes `\Shopsys\FrontendApiBundle\Component\HttpFoundation\ClientIpProvider` instead of `\Symfony\Component\HttpFoundation\RequestStack` — if you have extended this class, change your signature accordingly
    - use the same provider wherever you resolve the client IP address for a rate limiter of your own
- see #project-base-diff to update your project
