# MCP server

Shopsys Platform includes a production MCP server that exposes a small, read-only database exploration surface for external AI clients.

The MCP server is intended for tools such as Claude Code or Codex CLI. It does not include any built-in AI orchestration. It only exposes the MCP endpoint, authentication, schema discovery, and validated SQL execution.

## Available MCP tools

1. `getDatabaseTableNames`
    Returns the list of exposed database tables available to MCP clients.
2. `getDatabaseSchema`
    Returns the generated schema details for selected exposed tables, including columns, primary keys, and foreign keys.
3. `executeSql`
    Executes a validated read-only SQL query against the exposed schema through the dedicated read-only connection.

SQL validation uses the [`ext-pg_query`](https://flow-php.com/documentation/components/extensions/pg-query-ext/) PHP extension built on [`libpg_query`](https://github.com/pganalyze/libpg_query), so the query is parsed into a PostgreSQL AST and checked structurally against the exposed schema instead of relying on simple keyword matching.

## Authentication options

The MCP server supports two authentication paths.

### Manual token

This is the fallback path for clients that do not support the browser-based OAuth flow.

The administrator can:

- generate a manual MCP token
- regenerate it, which revokes the previous one immediately
- revoke it explicitly

The raw token is shown only once.

### Browser-based client authorization

This is the preferred path for clients that support OAuth-based login.

The flow is:

1. the client discovers the OAuth metadata
2. it registers itself dynamically
3. it opens the browser authorization page in the Shopsys administration
4. the administrator allows or denies access
5. the client exchanges the authorization code for an MCP bearer token

Connected-client tokens are stored per OAuth `client_id`. In the administration, the readable `client_name` is shown together with the technical `client_id`.

The detailed flow is described in [MCP browser authentication flow](./browser-auth-flow.md).

## Administration page

The MCP administration page is available under:

- `Settings > Superadmin > MCP server`

The current implementation is restricted to superadministrators even though the flow is otherwise described in general administrator terms.

The page currently provides:

- overview of authorized MCP clients
- revoke action for connected-client tokens
- manual token generation and revocation
- Claude Code setup instructions
- generic setup instructions for other MCP clients

## Runtime behavior

The MCP endpoint is exposed over HTTP and protected by a dedicated Bearer-token firewall. Authentication is separate from the browser administration session.

The generated MCP schema is stored in:

- `project-base/app/mcp-schema.json`

It is regenerated by:

- `shopsys:mcp:generate-schema`
- the post-migration integration based on `DatabaseSchemaMigratedEvent`

Runtime schema consumers read that generated artifact as the single source of truth.

This file is an internal runtime artifact. AI clients do not consume it directly; they access the exposed schema through the MCP tools.

The file does not contain the full Doctrine model or an inferred abstract contract. It contains the exposed PostgreSQL schema that MCP clients are allowed to work with:

- exposed table names
- exposed columns with PostgreSQL data types and nullability
- primary keys
- foreign keys

Example:

```json
{
  "administrators": {
    "primaryKey": ["id"],
    "columns": {
      "id": {
        "dataType": "INT GENERATED BY DEFAULT AS IDENTITY",
        "nullable": false
      },
      "email": {
        "dataType": "VARCHAR(255)",
        "nullable": false
      },
      "role_group_id": {
        "dataType": "INT",
        "nullable": true
      }
    },
    "foreignKeys": [
      {
        "columnNames": ["role_group_id"],
        "referencedTable": "administrator_role_groups",
        "referencedColumnNames": ["id"],
        "onDelete": "NO ACTION"
      }
    ]
  }
}
```

This artifact is then used by:

- `getDatabaseTableNames`
- `getDatabaseSchema`
- SQL validation for `executeSql`

## Exposure configuration

MCP exposure is explicit. Doctrine entities and their mapped fields are exposed only when they are marked with MCP attributes.

### Table exposure

Use `#[AsMcpTable]` on an entity class:

```php
#[AsMcpTable]
class Product
{
}
```

Or explicitly disable exposure:

```php
#[AsMcpTable(false)]
class AdministratorMcpToken
{
}
```

### Column exposure

Use `#[AsMcpColumn]` on mapped properties that should be exposed:

```php
#[AsMcpColumn]
protected $name;
```

Or explicitly disable a mapped field:

```php
#[AsMcpColumn(false)]
protected $secretValue;
```

For inherited or special field mappings, the attribute can also be declared on the class with `fieldName`:

```php
#[AsMcpColumn(fieldName: 'id')]
#[AsMcpColumn(fieldName: 'locale')]
class ProductTranslation extends AbstractTranslation
{
}
```

This is useful when the mapped property comes from a parent class you are not able to modify directly, for example translation entities extending `Prezent\Doctrine\Translatable\Entity\AbstractTranslation`.

`fieldName` is only valid on the class-level attribute. It must reference an existing mapped field or owning-side association.

## Static enforcement

The exposure coverage is enforced by the custom PHPStan rule `McpEntityExposureAttributeRule`.

That rule checks ORM entities in the `App\\` and `Shopsys\\` namespaces and requires:

- `#[AsMcpTable(exposed: bool)]` on every checked Doctrine entity
- `#[AsMcpColumn(exposed: bool)]` on every mapped scalar field, embedded field, and relevant owning-side association of an exposed entity

## Operational notes

- In production, `MCP_DATABASE_USER` and `MCP_DATABASE_PASSWORD` must point to a dedicated read-only PostgreSQL user, not to the main application database user.
- MCP access tokens are stored hashed in the database.
- Both manual and connected-client tokens expire.
- Query limits and statement timeout are configured through bundle configuration.
- Public MCP entrypoints are rate-limited as baseline abuse protection. Dynamic client registration and token exchange are limited by client IP. MCP runtime requests always consume an IP-based limit and also consume a token-public-ID limit when the bearer token has the generated token shape.
- MCP requests are logged to the dedicated `mcp` Monolog channel.
