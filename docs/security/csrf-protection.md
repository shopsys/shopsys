# CSRF Protection

Shopsys Platform uses several CSRF protection layers.  
This guide focuses on **when to use which one** and gives practical rules for daily development.

For implementation details, see:

- [`packages/framework/src/Twig/CsrfExtension.php`]({{github.link}}/packages/framework/src/Twig/CsrfExtension.php)
- [`packages/framework/src/Component/Router/Security/Attribute/CsrfProtection.php`]({{github.link}}/packages/framework/src/Component/Router/Security/Attribute/CsrfProtection.php)
- [`packages/framework/src/Component/Router/Security/RouteCsrfProtector.php`]({{github.link}}/packages/framework/src/Component/Router/Security/RouteCsrfProtector.php)

## Quick decision guide

Use this checklist when implementing UI actions:

1. **State-changing admin route action?**  
   Use route-level protection: mark the action with `#[CsrfProtection]` and generate links with `protectedUrl(...)`.
2. **Standard Symfony form?**  
   Use built-in Symfony form CSRF (default behavior).
3. **Login/logout security flow?**  
   Use firewall CSRF settings from security configuration.

## Do I need both `#[CsrfProtection]` and `protectedUrl(...)`?

Yes, in the standard route-level flow they are **complementary**:

- `#[CsrfProtection]` protects the target controller action (server-side validation).
- `protectedUrl(...)` generates a URL that includes the required route token (client-side link generation).

In practice:

- For state-changing admin route actions, use both.
- If you cannot use `protectedUrl(...)`, keep `#[CsrfProtection]` on the action and pass `routeCsrfToken` manually.

## Route-level CSRF for administration actions

Use route-level protection for actions triggered directly by links/buttons that change state (for example: set default, delete, enable/disable).

### Recommended usage pattern

1. Mark the controller action with `#[CsrfProtection]`.
2. Generate the action URL with `protectedUrl(...)`.
3. Keep this as the default pattern for custom admin actions.

Example:

```twig
{{ protectedUrl('admin_store_setdefault', { id: store.id }) }}
```

### Manual token passing (only when needed)

Use manual token handling only when `protectedUrl(...)` cannot be used (custom rendering or special URL construction).  
In that case pass `routeCsrfToken` explicitly.

## Existing places where route tokens are already handled for you

Before adding custom token logic, check whether your use case already goes through these helpers:

- **Grid action links** (`delete`, `reset password`) in
  [`ActionColumn`]({{github.link}}/packages/framework/src/Component/Grid/ActionColumn.php)
- **CRUD action links** generated by
  [`packages/administration/src/Twig/ActionExtension.php`]({{github.link}}/packages/administration/src/Twig/ActionExtension.php)
- **Confirm-delete modals** in
  [`ConfirmDeleteResponseFactory`]({{github.link}}/packages/framework/src/Component/ConfirmDelete/ConfirmDeleteResponseFactory.php)

Use these existing flows instead of duplicating token composition.

## Symfony form CSRF

For Symfony forms, CSRF is enabled globally and should be your default choice.

- Global config:
  [`project-base/app/config/packages/framework.yaml`]({{github.link}}/project-base/app/config/packages/framework.yaml)

Typical rule:

- **Keep CSRF enabled** for forms that mutate data.
- **Disable CSRF only for specific GET/search forms** where token protection is not needed.

Examples of search-style forms with disabled CSRF:

- [`packages/framework/src/Form/Admin/QuickSearch/QuickSearchFormType.php`]({{github.link}}/packages/framework/src/Form/Admin/QuickSearch/QuickSearchFormType.php)
- [`packages/framework/src/Model/AdvancedSearch/AdvancedSearchFormFactory.php`]({{github.link}}/packages/framework/src/Model/AdvancedSearch/AdvancedSearchFormFactory.php)

## Login/logout CSRF in security configuration

Authentication flows use Symfony Security CSRF settings and should follow existing configuration.

- Security config:
  [`project-base/app/config/packages/security.yaml`]({{github.link}}/project-base/app/config/packages/security.yaml)
- Logout route usage with token parameter:
  [`project-base/app/config/shopsys-routing/routing_front_en.yaml`]({{github.link}}/project-base/app/config/shopsys-routing/routing_front_en.yaml)
- Administration layout logout token usage:
  [`packages/administration/templates/layout/layout.html.twig`]({{github.link}}/packages/administration/templates/layout/layout.html.twig)

## Team recommendations

- Prefer **existing helpers** (`protectedUrl`, grid/CRUD/confirm-delete flows) over custom token handling.
- Treat route-level protection as the default for **state-changing admin route actions**.
- Keep implementation details secondary in feature docs; focus on correct usage and safe defaults.
